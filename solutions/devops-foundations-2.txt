QUESTION
========
## Scenario

ShopSphere is an online shopping site. Today it is one large application (a monolith) that contains the product catalog, the shopping cart, payments, orders and email notifications. The team is considering splitting it into microservices. Before deciding, they want a clear comparison.

Everything you need is in `/home/user/architecture/`:

- `usecase.md` describes ShopSphere.
- `statements.txt` contains numbered statements (`S1`, `S2`, ...) about microservices. Some describe real operational **benefits**, some describe real operational **challenges**, and some are **false**.
- `traits.txt` contains numbered traits (`T1`, `T2`, ...), each describing either a monolith or a microservices architecture.

## Tasks

### Task 1: Two operational benefits

Create `/home/user/architecture/benefits.txt` with the IDs of **two** statements that are real operational benefits of microservices, one ID per line.

### Task 2: Two operational challenges

Create `/home/user/architecture/challenges.txt` with the IDs of **two** statements that are real operational challenges of microservices, one ID per line.

### Task 3: Classify the traits

Create `/home/user/architecture/traits-answer.txt` with one line per trait in `traits.txt`, in the form `ID=monolith` or `ID=microservices`, for example:

```
T1=monolith
```

## Notes

- Do not pick a false statement in Task 1 or Task 2.
- Use exactly two IDs in each of `benefits.txt` and `challenges.txt`.

## Expected outcome

Three answer files that identify two benefits, two challenges and the architecture each trait belongs to.

ANSWER
======
The statements are numbered in a random order for every lab session, so pick them by meaning.

**Benefits** (choose any two):

- Each service can be deployed on its own, so a cart fix does not need a full site release.
- A busy service, such as the catalog during a sale, can be scaled without scaling everything else.
- A failure in one service, such as notifications, can be isolated so the rest of the shop keeps working.

**Challenges** (choose any two):

- Calls between services go over the network, which adds latency and new ways to fail.
- Tracing one customer request across many services needs centralized logging and tracing.
- Keeping data consistent across services (for example orders and payments) is harder without one shared transaction.

**False statements** (never choose): microservices remove the need for monitoring, always cost less to run, or require every service to use the same database and language.

**Traits:**

| Trait | Architecture |
| --- | --- |
| One deployable artifact for the whole shop | monolith |
| A bug in payments can crash the whole application process | monolith |
| All modules share one database schema | monolith |
| Teams release their service on their own schedule | microservices |
| Components talk to each other through network APIs | microservices |
| Each service can use the technology that suits it | microservices |

APPROACH
========
1. Read `usecase.md`, then read `statements.txt` line by line.
2. Sort every statement into benefit, challenge or false. Keep two of each of the first two groups.
3. For each trait, ask whether it describes one deployable application or many small services.
4. Write the three answer files with `nano` or `echo`, then check them with `cat`.

HINT
====
- "Operational" means about running the system: deploying, scaling, failures, monitoring.
- A benefit of microservices usually comes from services being independent. A challenge usually comes from the network between them and from having many moving parts.
- Be careful with absolute words such as "always" or "never": they often mark a false statement.

ORIGINAL SOLUTION SCRIPT (solve.sh)
===================================
#!/bin/bash
set -euo pipefail
cd /home/user/architecture
pick() { grep -E "$1" statements.txt | head -n2 | cut -d: -f1; }
pick 'deployed on its own|scaled without|isolated' > benefits.txt
pick 'over the network|Tracing one|consistent' > challenges.txt
: > traits-answer.txt
while IFS= read -r line; do
  id=${line%%:*}
  case "$line" in
    *"One deployable"*|*"crash the whole"*|*"share one database"*) kind=monolith ;;
    *) kind=microservices ;;
  esac
  echo "$id=$kind" >> traits-answer.txt
done < traits.txt
